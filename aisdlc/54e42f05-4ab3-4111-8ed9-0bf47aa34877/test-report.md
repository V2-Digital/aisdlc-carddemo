## COBOL-vs-Java differential (`legacy/tests/cbtrn02c_equiv.sh`)
The script runs the real COBOL through `run.sh` with `INPUT_DIR` and runs the Java jar, then compares `TRANFILE`, `DALYREJS`, `ACCTFILE`, `TCATBALF`, `SYSOUT` and the RC. Fixtures are in `legacy/tests/cbtrn02c_equiv/<case>/`, regenerated by `gen_fixtures.py`. `golden/` and the harness are untouched.

All 17 cases match byte for byte: unknown card (100), missing account (101), 102 boundary, 103 over 102, blank expiry (D7), zero and negative amounts, zero-result sign (`{`), first-create FILLER, create-after-read FILLER (`Z`s inherited), update existing, no rejects (RC 0), empty DALYTRAN (RC 0), CURR-BAL / CAT-BAL overflow (D5), WS-TEMP-BAL overflow (D9), negative debit (D1), same account twice, duplicate TRAN-ID.

Findings from the differential:
- The sticky TCATBAL FILLER model is **confirmed** against GnuCOBOL, both ways.
- Truncation modulo 10^11 and 10^12, and the `{` sign for zero, **match** COBOL. The unit-test expectations for D5 and D9 are therefore COBOL-verified.
- **Duplicate TRAN-ID: both abend with RC 16.** `run.sh` deliberately exports no outputs on any RC other than 0 or 4, so the partial-state outputs (D6) can't be compared against COBOL. D6 is pinned only by the Java unit test, which follows the source order. This is a **gap**.

## Iterations
1. First `mvn verify`: 2 test-side failures. The Overpunch test expected `-0` (`}`) to re-encode as `{`, but it is a decode-then-encode of a non-canonical input. The D4 test searched for the wrong source string. Both were test bugs. `src/main` was not changed.
2. The first fixture generator put the amount at the wrong offset. Every case rejected as 100/102 on both sides, so the cases agreed but proved little (RC 4 everywhere). I noticed the suspicious RCs, rewrote the generator with the correct offsets and re-ran: the 17 cases now exercise the intended paths (RC 0 where expected).
